\section{Fundamentação Teórica}\label{sec:fundamentacao}

Esta seção apresenta os conceitos necessários para compreender o fuzzer e o
experimento. O texto separa três elementos que às vezes são tratados como se
fossem um só: o contrato da API, usado para gerar e verificar casos; a
execução, que observa o comportamento do serviço; e a priorização, que ordena
os achados depois da execução.

\subsection{APIs REST, HTTP e contratos}

REST é um estilo arquitetural para sistemas distribuídos, definido por
restrições como identificação de recursos, interface uniforme, comunicação
stateless e uso de representações transferidas entre cliente e servidor
\cite{fielding2000rest}. Uma API REST expõe essas operações por meio de uma
interface acessível pela rede; na prática, HTTP fornece a semântica dos
métodos, das respostas, dos códigos de status e dos cabeçalhos
\cite{rfc9110}. A presença de HTTP e JSON, isoladamente, não garante que uma
API siga todas as restrições de REST.

Um contrato de API descreve parte do comportamento esperado entre cliente e
servidor. Ele pode declarar quais operações existem, quais parâmetros são
aceitos, como os dados são representados e quais respostas são esperadas. Essa
descrição permite verificar propriedades observáveis, mas não substitui as
regras de negócio que não foram registradas no contrato.

\subsection{OpenAPI e JSON Schema}

OpenAPI é uma especificação independente de linguagem para descrever APIs HTTP
\cite{openapi311}. No fuzzer, os elementos mais relevantes são as operações
em \texttt{paths}, os parâmetros de rota, consulta e cabeçalho, o
\texttt{requestBody}, as respostas declaradas e os componentes reutilizáveis
por meio de referências \texttt{\$ref}. O documento também pode declarar
esquemas de segurança, que orientam a forma de autenticar as requisições.

Os schemas associados a entradas e respostas expressam restrições sobre os
dados. Em OpenAPI 3.1, essas restrições seguem o vocabulário do JSON Schema;
palavras-chave como \texttt{type}, \texttt{required}, \texttt{enum}, limites
numéricos, padrões e propriedades descrevem parte da estrutura válida
\cite{jsonschema202012}. A validação de schema, entretanto, não descreve por
si só dependências entre chamadas, efeitos persistentes, permissões ou regras
de negócio.

Neste trabalho, o suporte ao contrato é deliberadamente parcial. O executor
interpreta o subconjunto de OpenAPI implementado pelo projeto e registra a
versão e a configuração utilizadas. Portanto, uma divergência observada só é
interpretada em relação às declarações efetivamente carregadas; ela não é uma
afirmação sobre todo o comportamento possível da aplicação.

\subsection{Teste negativo e fuzzing de APIs}

Teste negativo exercita entradas que deveriam ser rejeitadas, limites e
combinações que podem revelar tratamento inesperado. Fuzzing é uma forma
automatizada de gerar e executar muitas entradas, registrando as respostas
obtidas. Na geração \emph{geracional}, os casos são construídos a partir de um
modelo; na geração \emph{mutacional}, entradas existentes são transformadas.
Casos estruturados podem combinar as duas estratégias.

Em APIs REST, a geração precisa respeitar a estrutura de parâmetros e corpos
JSON, além de lidar com autenticação, dependências entre recursos, estado e
serialização. O survey de Golmohammadi, Zhang e Arcuri organiza esses desafios
e mostra que o contrato é uma fonte frequente de informação para geração e
validação, mas não resolve sozinho o estado da aplicação ou a completude do
oráculo \cite{golmohammadi2023rest}.

Ferramentas existentes exploram pontos diferentes desse espaço. RESTler deriva
sequências stateful e dependências produtor--consumidor a partir do contrato
\cite{atlidakis2019restler}. RESTest combina restrições e geração black-box
\cite{martinlopez2020restest}. Schemathesis deriva testes baseados em
propriedades a partir de schemas de APIs \cite{hatfielddodds2022schemathesis},
enquanto RestTestGen organiza parser, geradores, mutadores e estratégias de
execução em uma arquitetura modular \cite{corradini2022resttestgen}. Essas
abordagens mostram que “usar OpenAPI” não identifica uma técnica única: os
fuzzers diferem no modo de gerar casos, modelar estado e decidir se uma
resposta merece investigação. Comparações entre ferramentas também destacam
dependências, autenticação, dados realistas e reprodutibilidade como fatores
que afetam os resultados \cite{zhang2023openproblems}.

O fuzzer deste trabalho permanece \emph{black-box}: ele não instrumenta o
código da aplicação nem utiliza cobertura interna para orientar a geração. A
informação disponível para o ciclo é o contrato, a configuração da campanha,
as requisições enviadas e as respostas recebidas.

\subsection{Contrato como oráculo parcial e evidência de execução}

Um oráculo de teste é o mecanismo usado para decidir se o comportamento
observado é compatível com o esperado. Neste projeto, o contrato OpenAPI
funciona como um \emph{oráculo parcial}: fornece expectativas verificáveis
sobre método, parâmetros, formato, status e schema, mas não cobre tudo que
seria necessário para afirmar que a operação está correta ou segura. Essa é
uma síntese operacional do estudo, e não uma propriedade que a especificação
OpenAPI declare formalmente.

Por isso, um achado representa uma divergência observada entre a requisição,
a resposta e as expectativas interpretadas do contrato. Ele não é tratado
automaticamente como vulnerabilidade, causa raiz ou impacto de segurança. Uma
resposta inesperada pode resultar de regra de negócio não documentada, estado
residual, autenticação, dependência externa ou defeito do serviço; a evidência
registrada deve permitir que essa hipótese seja investigada depois.

O estado também interfere no resultado. Operações podem criar, alterar ou
remover recursos, depender de dados previamente existentes e exigir credenciais
ou uma ordem específica. Assim, uma campanha precisa registrar o contrato, a
versão do alvo, os parâmetros de execução, a autenticação aplicável e os
artefatos que permitem correlacionar plano, requisição, resposta e análise.
Reset, concorrência controlada e repetição com configuração fixa reduzem
variações experimentais, mas não transformam a observação black-box em
explicação da causa interna.

Para manter o vocabulário do experimento explícito, o projeto usa os seguintes
termos operacionais. Uma ocorrência é uma execução individual de um caso. Um
achado é uma ocorrência que passou por algum detector de divergência. Uma
assinatura reúne achados com o mesmo padrão observável, e uma família é o
conjunto deduplicado usado para contar esse padrão nas análises. Esses termos
organizam os artefatos do projeto; não são definições universais da literatura
de fuzzing. A deduplicação reduz repetição na triagem, mas não identifica a
causa raiz.

\subsection{Lógica fuzzy e inferência de Mamdani}

Na lógica clássica, um elemento pertence ou não pertence a um conjunto. Na
lógica fuzzy, uma função de pertinência atribui um grau entre zero e um para
representar quanto uma observação se enquadra em um conceito gradual
\cite{zadeh1965fuzzy}. Esse grau não é uma probabilidade: indica pertinência a
um conjunto linguístico definido pelo modelo.

Um sistema de inferência fuzzy recebe variáveis de entrada, calcula suas
pertinências, aplica regras linguísticas e combina as ativações em uma saída.
Na formulação de Mamdani, as regras têm a forma “se ... então ...” e a saída
é obtida pela agregação das conclusões e por uma etapa de desfuzzificação
\cite{mamdani1975}. O resultado é interpretável porque pode ser acompanhado
pelas entradas, pelas funções de pertinência e pelas regras que contribuíram
para a decisão.

No fuzzer, o sistema fuzzy não decide se existe um achado. Essa decisão é
produzida pelos analisadores, que comparam a resposta observada com o contrato
e com os detectores definidos pelo projeto. O sistema fuzzy recebe sinais do
achado e produz uma prioridade técnica para a triagem. A separação evita
confundir “detectar uma divergência” com “ordenar as divergências para análise”.

As funções, faixas e regras do FIS são escolhas do projeto. A literatura sobre
lógica fuzzy fundamenta a forma de representar e combinar sinais, mas não
determina que contradição comportamental, força da evidência ou exposição de
controle de acesso devam receber valores específicos neste estudo. A validade
dessas escolhas depende da descrição do modelo e da avaliação experimental
apresentadas nas seções seguintes.

\subsection{Prioridade técnica, severidade e impacto}

Na literatura de testes, priorização costuma significar reordenar casos para
atingir primeiro um objetivo, como detectar falhas mais cedo durante testes de
regressão \cite{elbaum2002prioritization}. Trabalhos que usam lógica fuzzy
nesse contexto combinam sinais dos casos para definir a ordem de execução
\cite{alakeel2014fuzzy}. O sistema deste projeto resolve um problema diferente:
os casos já foram executados, e a saída fuzzy ordena os achados que serão
triados.

Por isso, \emph{prioridade técnica} é uma definição operacional deste TCC. Ela
expressa quão urgente é analisar uma divergência à luz dos sinais disponíveis
no artefato, não uma medida universal de severidade, explorabilidade, impacto
de negócio ou probabilidade de vulnerabilidade. Um status HTTP, um tamanho de
resposta ou uma divergência estrutural podem justificar investigação, mas não
determinam sozinhos o efeito de segurança.

Essa distinção evita atribuir ao score uma decisão que ele não toma. O modelo
ajuda a ordenar evidências para triagem; a confirmação de causa, impacto e
vulnerabilidade exige análise adicional do alvo e não faz parte do mecanismo
fuzzy descrito aqui.

\subsection{Síntese conceitual}

O encadeamento teórico do projeto pode ser resumido assim:

\begin{enumerate}
    \item o contrato OpenAPI delimita operações, dados e respostas que podem
    ser exercitados;
    \item o gerador produz casos válidos, inválidos e mutados a partir desse
    contrato;
    \item o executor envia as requisições e preserva as respostas em uma
    campanha identificável;
    \item os analisadores comparam observações com as expectativas
    interpretadas do contrato;
    \item os achados são agrupados em assinaturas e famílias para reduzir
    repetição;
    \item o sistema fuzzy atribui prioridade técnica aos achados agrupados;
    \item a triagem humana interpreta as evidências e decide quais resultados
    merecem investigação adicional.
\end{enumerate}

Esse fluxo delimita a contribuição do trabalho: produzir evidências
reproduzíveis a partir de contratos OpenAPI e oferecer uma ordenação
interpretável para sua triagem. Ele não promete modelar todas as regras das
APIs, medir cobertura de código ou confirmar automaticamente vulnerabilidades.
